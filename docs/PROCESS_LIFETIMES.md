# Process ownership and lifetimes

## Implemented source boundaries

The Windows .NET stdio adapter acquires one of a bounded set of installation-local file leases before initializing its MCP host. Exclusive open handles, rather than saved PIDs, represent active clients. The operating system releases handles after process exit; stale slot metadata is never authority to stop a process. Lowering the configured limit counts all held slots and never evicts another client. Admission inspects at most sixteen slots under one short-lived admission lock.

The adapter pins process handles for its direct parent and launcher wrappers (`powershell`, `pwsh`, `cmd`), up to four ancestors. Capture rejects a missing, exited or reused identity. An observed owner exit requests host shutdown. Stdio EOF uses the MCP SDK's normal host shutdown path. The configured host shutdown timeout bounds cooperative host shutdown; it is not a process-kill guarantee for a stuck native library.

Each frontend owns its admission lease and observation handles. It does not own the shared HTTP service, another frontend, GUI, watch or native job. Disconnecting does not cancel shared work or establish rollback. No process is terminated using a stale PID file or a process-name sweep.

The optional Python supervisor marks its own launched .NET service as supervised. That service observes the supervisor's pinned parent identity and requests shutdown on owner loss. The supervisor now uses framework 0.20's durable contained launcher rather than `Popen`. Controlled exit and failure after launch close its exact job through the retained resource record and receipt contract. Reporting errors remain nonfatal; a resource-ledger invariant failure stops this controlled offline tree rather than continuing untracked. The directly launched service intentionally persists independently of its launching shell. The optional Python MCP frontend does not yet share .NET frontend admission/owner monitoring.

A `.local/maintenance-hold.json` marker blocks ordinary source launchers, GUI connections, installer/configurator/runtime-selection mutations and the source .NET/Python server entry points. Its presence requires explicit operator release; no cleanup or reconnect path clears it automatically. Previously installed executables still need separate version verification.

## Owned service process tree

The Windows service source now enters an unnamed, non-inheritable-handle Job Object before business services or workers are initialized. The job uses `KILL_ON_JOB_CLOSE` and an active-process bound without breakaway flags. The owning service and ordinary children created from it share membership from creation; there is no post-launch PID sweep or assignment race. A containment setup failure refuses service startup. `MaximumOwnedProcesses` defaults to 32, accepts 1..128, includes the service and applies on its next start.

The sole job handle remains rooted for the entire service process lifetime. It is intentionally not disposed by the host/DI shutdown path: closing it while the service is still inside its own job would terminate the owner before cleanup/journaling completed. OS process exit closes that handle, providing the intended inherited-child cleanup boundary even after abrupt owner exit. Graceful worker disposal remains the first cleanup path. Abrupt termination does not make partial effects safe or certain.

Existing user-owned applications are never assigned to this job. A shared service keeps its own job independently of any frontend's lifetime. Normal child creation inherits Windows job membership, but WMI creation, external COM/service hosts and existing native applications may be outside it. See Microsoft's [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [job limit definitions](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information). Native launch/attachment behavior still requires specific acceptance.

New FactoryTalk Studio GUI launch through the service is blocked with `native_gui_ownership_required` until durable ownership and dirty-state recovery are integrated. The former fire-and-forget launcher did not retain that information. This prevents adding an unsaved native GUI to the service's kill-on-close tree without a recovery contract. Operators can launch Studio themselves and continue using file preparation/validation and read-only window status. Those applications are never claimed or terminated by this service.

Authenticated `/api/management/activity` adds `process_containment` with the selected profile, configured cap, OS-reported active count or explicit unavailability, unknown external native effects and `not-integrated` durable recovery. It exposes no process command lines, project names or cleanup action. This metadata does not authorize manager restart or substitute for a durable resource ledger.

## Durable supervisor service-tree records

`rockwell_framework.ownership` uses the reviewed framework `ResourceLedger` and a `ResourceOwner` living in the actual supervisor process. The same explicit registry is passed to the manager reporting registration and ledger. A temporary CLI helper is never the owner. The framework writes a reservation, creates the background service suspended with an atomic Windows job association, binds its host/PID/creation-time/image identity durably, then resumes execution. There is no uncontained fallback and no inherited stdio.

The supervisor polls using a pinned identity-checked process handle, periodically retains current member identities and writes version-2 private supervisor metadata with the owner/resource IDs and registry. Native applications outside the inherited job still require separate records. Membership includes verifiable intermediate launchers/console hosts but is not a complete process-audit history. Cleanup intents/uncertain receipts remain in the ledger across restarts; this app does not automatically reconcile, clear barriers or replay cleanup.

For a version-2 managed instance, `Stop-Service.ps1` verifies its current process creation identity and writes a private HMAC-signed stop intent bound to the exact owner/resource generation. The running supervisor authenticates that intent and closes its own tree through the ledger API. The script observes process exit and a terminal cleanup receipt; it never uses PID termination for this managed path. An existing same-generation stop intent keeps its request ID, and terminal/uncertain resource records reject replacement effects. The request stores a signature, not the service key. This is an explicit operator stop of the controlled offline profile, not manager restart permission or an MCP tool. The legacy direct-service stop path remains separate and still requires ownership hardening.

This first managed profile is explicitly `offline-contained-v1`. Python rejects configured SDK/CIP paths, enabled controller operations and controller targets before registering or launching anything. Core rechecks the effective configuration before business services are initialized, so a settings/startup race cannot enable native work. `MaximumOwnedProcesses` supplies the 1..128 inherited-process bound. The shared ledger also retains its separate default bound of 32 active app resource records and 4,096 historical records.

The gate does not edit settings, disable a target or switch routes. A native-enabled installation cannot select this managed profile until the app-owned .NET/native registration and recovery adapter is implemented and accepted. Direct .NET startup still has its existing separate route and is not claimed to have durable ledger coverage. The background launcher is not suitable for MCP stdio; the current SDK transport is retained. Child stdout/stderr are not inherited by this launcher, so historical redirected service logs are not new launch evidence. Supervisor diagnostics and retained resource/job records remain separate.

## Remaining ownership work

The inherited-tree foundation has harmless process-fixture acceptance only. The reviewed framework 0.20.0 package supplies the language-neutral resource ledger and contained background launcher; the app supervisor now integrates those for its offline-only service tree. Core also has an [interoperable native .NET ledger component](RESOURCE_LEDGER.md) tested against that package. Production native/direct-service launch-path wiring, native resource policy and installed acceptance remain outstanding. Native .NET bindings are app-owned rather than supplied by the framework.

The application must separately track exclusive launches, user-owned attachments and shared leases; pin process creation identities; retain dirty/uncertain evidence; and keep shared resources alive until their last authorized owner closes. Native SDK/COM/server-owned processes may fall outside a normal child tree. User-owned engineering applications must never be inferred to be disposable from their names or current project.

Existing native job receipts, extension indeterminate outcomes and restart barriers remain authoritative. A process exit is not proof that external engineering effects stopped or rolled back. No owner-loss path retries, reconciles or clears an uncertain operation.

## Validation

`McpClientLifetimeTests` exercises configuration bounds, file-handle admission, released/stale slots and lowering limits using generated temporary files. `OwnedProcessContainmentTests` checks policy, native ABI structure sizes, pre-entry metadata and rejected GUI launch; it never assigns the test runner to a job. `ManagedResourcePolicyTests` checks native/profile refusal without launching anything. `framework/tests/test_owned_child.py` tests orchestration with stubs; `test_ownership.py` uses real retained ledger bytes with a synthetic process driver, including failed identity publication, protected native profiles and uncertain cleanup without replay.

`framework/tests/test_ownership_processes.py` is opt-in with `ROCKWELL_HARMLESS_RESOURCE_TESTS=1` on Windows. It launches only disposable Python processes in explicit private fixture registries. It verifies recorded descendants and their closure, pinned-handle exit codes, owner-crash containment and reviewed orphan retirement without replay. Windows interpreter redirectors and console hosts are retained as observed members too. An outer fixture job contains crash-test helpers for bounded cleanup. These checks do not execute the actual .NET service, an MCP transport or native engineering applications.

`Verify-OwnedServiceStop.ps1` tests the managed stop script using synthetic files and process-object stubs under both PowerShell 7 and Windows PowerShell. It checks the shared Python/PowerShell HMAC vector, retained request ID, receipt readback, terminal-repeat denial and changed-creation refusal. It never looks up or stops an actual PID. Actual service shutdown through this channel remains a controlled runtime canary check.

Isolated runtime acceptance remains required for stdio EOF, parent and wrapper exit, abrupt frontend/supervisor death, simultaneous admission, startup failure, shutdown during a blocked operation and instance-count recovery. Later native acceptance must prove exclusive resource cleanup, preservation of user-owned attachments, shared last-owner behavior and durable dirty/uncertain evidence. These checks require an explicitly released runtime hold and disposable fixtures. Ordinary reconnect or installation is not acceptance.
