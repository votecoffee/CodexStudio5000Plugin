# App protocol features and acceptance

Find `protocol.features` in `rockwell_broker_capabilities` and call its exact discovery arguments through `rockwell_read_workflow` for the selected .NET route's implementation report. The normalized catalog v1 schema and fixed tools stay unchanged. The explicit Python `--skills` endpoint also exposes `rockwell_protocol_doctor` with its live guidance revision/generation. These are read-only metadata reports; they select no project, inspect no job files and grant no authority. The service version and a particular chat's current catalog still need separate verification.

| Feature | Selected direct .NET route | Explicit Python profile and remaining work |
|---|---|---|
| Current workflow guidance | Enabled and tested: three bootstrap skills use existing pinned workflow/reference readers | One canonical `workflows/` source; Core embeds full text, source SHA-256 and named references |
| Frontend lifetimes | Implemented, runtime acceptance pending: bounded file leases and pinned parent/wrapper handles in the Windows .NET frontend | GUI settings apply to new frontends; optional Python admission/owner monitoring remains outstanding. | Discovery caching | Blocked: current publication is transient/legacy, TTL zero, watching off; no assessed hints | Guidance bytes are instance-local immutable snapshots reused only after one fresh app revision read. This is not cached tool authorization. Retained modern ownership, TTL hints and event invalidation need app-owned assessment before changing the downstream profile |
| Progress | Blocked: native jobs are not bound to a per-request MCP progress relay | Existing SDK events/extension structured job state remain usable. Future adapters must report real monotonic stages, with no fabricated percentage or cross-request delivery |

Implement app-owned operation IDs, owner authorization, durable start lookup and exact route revisions before `TaskExtension`/`TaskRoute`; never replay start to discover outcome |
| Modern approval continuations | Blocked: no app-owned elicitation resolver bound to exact engineering target/review | Existing preview/review tokens and current policy still apply. Do not fabricate approval, alter a chat's approval mode or add prompts to read-only metadata |
| Engineering artifact resources | Blocked: no owner-bound bounded MCP resource adapter or authorized artifact update feed | Existing authenticated artifact readers remain available. Add scoped immutable source/version/hash/freshness identities and authorization on each read/notification before exposing reports or previews as resources |
| Tray management | Reporting implementation tested in isolated normal launch/stop; actual production registration is separately enabled | Uses framework `ManagedService`, cached `ManagedStatus`, component versions, canonical plugin ID and random instance IDs. Restart is disabled: no atomic fence across all chats, unsaved GUI documents, prepared reviews and unresolved native effects |
| Native worker owner loss | Implemented, runtime acceptance pending: source Windows service enters a bounded private kill-on-close job before worker initialization | Controlled supervisor cleanup/owner observation also have source implementations. Real tree cleanup, durable resource recovery, attachment preservation and external-effect acceptance remain outstanding. Never equate process exit with rollback |
| OAuth, Redis, MCP Apps | Outside this local workflow / deferred | No remote endpoint, replica or second native-state owner. Generic downstream Tasks/Apps forwarding and some continuation relays are framework limitations, not activated features |

## Validation boundaries

The app-owned package uses the reviewed framework 0.20.0 wheel and Python MCP SDK 2.3.0; the direct .NET SDK remains independently locked at 2.2.0. `python -m rockwell_framework.package --wheel ...` verifies wheel SHA-256, RECORD and installed payloads. A dependency's capabilities do not enable this app's optional protocols.

`framework/tests/test_guidance.py` tests real `SkillCatalog`/`ExtensionServer` requests through a retained modern client using generated app metadata, including exact bytes, stale cursors, concurrent/stale publication, failed candidates, source changes during reads, add/remove, catalog isolation and explicit CLI selection. `scripts/verify_guidance.py` checks authenticated HTTP and stdio with the installed app wheel, all three actual shared Core guides and seven references; it refuses controller/native-enabled fixtures. The existing default profile's fourteen tool definitions, direct 59-tool schemas, effect policy, preview/apply and durable reconciliation tests remain separate.

Source, built package, protocol transport, installed production route, native Codex activation and native Studio/controller acceptance are separate layers. Local deployment receipts stay in ignored private state. Existing indeterminate effects and durable write barriers are not cleared, retried or inferred to have completed by these metadata tests.
